## 1. 目标与范围

让快捷浮层和侧栏共用常用和弦配置、目录和一份和弦草稿。两处都有固定字面“更多 ⌄”，打开搜索、调性推荐、完整库与配置入口。用户在完整库先选和弦，再选具体 voicing（同一和弦的不同指法），回填当前草稿后，仍由“应用和弦”一次写入谱面。

本期完整目标为 12 个根音音级 × 16 种性质，共 **192 个 canonical identities**。性质为 `major, m, 7, maj7, m7, dim, dim7, m7b5, aug, sus2, sus4, add9, 6, m6, 9, m9`。异名同音 aliases 不重复计数；每个 identity 至少一个通过审核且可弹奏的标准调弦指法，热门和弦支持 2–3 个指法。系统预置以版本化 JSON **保存在本项目仓库**，由网站 `public/assets/chords/` 提供同源 HTTP 静态资源；本期不接入任何第三方存储。数据格式保留未来迁移到对象存储/CDN 的可能。**这是交付计划，不是当前库规模或本轮完成结果。**分阶段实施不能把只有名称、没有指法的项目算作已覆盖。

调性推荐支持 12 个主音音级 × 大小调：默认只列自然调内三和弦和七和弦，小调另列和声小调常用 `V / V7 / vii° / vii°7`。借用和弦、次属和弦、其他调式与 slash voicings 全覆盖不在本期；自由名称继续允许，不强迫归入系统词典。系统库只读，用户可保存自定义收藏；“我的常用”配置和收藏仅在浏览器本地持久化，并支持独立 JSON 配置文件导入导出，不能改变曲谱调性。

图形编辑在一层 Modal 内完成，保留六弦表单替代路径、局部撤销、错误定位和最后合法预览。沿用谱 schema v8，不把 catalog identity、voicing id、临时筛选调性或用户库引用写进谱文件；**新增正式持久化曲谱信息** `score.meta['lxm:tonality']`，表达主音、大小调与小调简谱记法。它与用户配置分开，不新增谱顶层字段、不升 schema；不能将本期描述成“不新增任何谱数据”。

## 3. 状态归属与 Module 设计

采用 `codebase-design` 的 Module、Interface、Seam 术语。目标是让目录规则、编辑事务和持久化错误各自集中，调用方只传业务意图；不另建全局音乐草稿 store，不为每个按钮增加一层转发 Module。

### 3.1 Chord catalog Module：身份、推荐与快照

拟放在 `packages/lxm-editor/src/core/chord-catalog.ts`，维护纯数据校验、查询和复制逻辑；系统目录数据改为独立 JSON，不再新增手写 `chord-catalog-data.ts` 数组。权威 JSON 放在本项目网站 `public/assets/chords/` 并纳入 Git，由 Next.js 静态服务直接提供；HTTP 请求由第 3.7 节的网站资源 Module 执行，核心不依赖 fetch、React 或浏览器存储。这是两处入口、Dropdown、完整库和配置共用的 Interface：

以下类型和函数为 Interface 示意，并非可编译的生产实现；`ChordQuality` 对应第 1 节列明的 16 个性质，其余结果类型、错误与接入细节在实施中定义，不暗示现有 enum 已含这些值。

```ts
type ChordIdentity = { rootPc: number; quality: ChordQuality };
type ChordCatalogQuery = {
  text?: string;
  rootPc?: number;
  quality?: ChordQuality;
  key?: { tonicPc: number; tonicSpelling: string; mode: "major" | "minor" };
};
// catalog 是不可变目录值；推荐结果含调式拼写和级数，snapshot 含独立数组。
queryChordCatalog(catalog, query): ChordCatalogResult;
copyCatalogVoicing(catalog, identityId, voicingId, spelling?): ChordSnapshotResult;
```

`identityId` 由根音音级和性质组成，例如 `pc:1/major`；`C#` 和 `Db` 是同一 identity 的拼写。`voicingId` 是该 identity 下稳定的指法身份，不用数组索引或图的 JSON 充当长期配置 id。目录记录含 canonical name、aliases、每个 voicing 的完整 diagram、指型标签及低音，审核证据按第 5.4 节关联到版本记录。查询负责别名匹配、性质过滤、按调性级数排序和拼写；copy 负责存在性检查和深拷贝，找不到返回具名错误，不静默选择另一个 voicing。

用户自由名称无需反向解析成功。系统身份只在选择目录或收藏时存在于内存，手工改名称或改图后清除“当前精确匹配”提示，不损坏音乐草稿。重开谱时可按名称与图精确识别，失败即显示自定义，不据推测重置名称/图。旧 `CHORD_PRESETS/copyChordPreset` 可在迁移期间保留兼容用途；本轮新入口统一读取已加载的 JSON 目录，不继续扩写旧 TypeScript 数组，也不将它暗中用作另一份系统库或网络失败兜底。同步旧 Interface 的去留按实际调用情况处理，不为 HTTP 加载向核心引入异步全局注册。

### 3.2 Chord editing Module：同一 owner 下的表面切换与回填

拟放在 `apps/website/components/EditorShell/chord-edit-session.ts`。唯一父草稿仍由 `MusicTextSidebar` 持有；此 Module 收拢“捕获目标与版本、打开表面、检查 token、完成或取消”的行为，不复制父草稿的长期所有权。

Interface 采用少量具名操作：`open(kind, context, seed?)`、`complete(token, result)`、`cancel(token)` 和只读状态。context 接收读取当前会话、读写父草稿、解析目标、Modal controller、恢复焦点的依赖。`kind` 为 library/custom；状态只允许 idle/library/custom 之一。token 包含 owner token、generation、target key、打开时 EditorSessionVersion 和本次 request id；回填还校验父草稿基线未被外部改写。UI 只能提交 token 与值，不能自行调用 `SetChordSymbol`。

现有 `useEditorDraftRecords` 的 owner 在 hook 内部，返回 handle 只暴露 `invalidateOwner()`，不能假定调用者已能捕获协调器身份。本期最小扩展该 handle 为 `captureIdentity()` 与 `isCurrent(identity)`，令 token 使用同一个 owner/generation；Sidebar 原有离开流程统一调用该 handle 失效，原 `ownerGeneration` 若保留仅作为其镜像，不再独立计数。登记、Modal 回填与设置暂停必须共享同一身份，不能另造一个不随原离开路径失效的 owner。该变更限于所需 Interface，并回归现有其他草稿登记行为。

表面职责：`ChordQuickEditor/ChordEditor` 是受控编辑表面；共享 `ChordPresetControls.tsx` 呈现快捷项及固定入口；`ChordLibraryModal.tsx` 保存当前浏览/选择副本；`ChordDiagramEditorModal.tsx` 保存独立 local buffer。折叠、隐藏 popover 或打开 Modal 只改变可见性，不能触发离开流程、递增 generation 或销毁父 owner。

### 3.3 Chord diagram editing Module：原子草稿编辑

拟放在核心 `chord-diagram-edit.ts`。Interface 为纯函数 `editChordDiagram(diagram, intent)`，返回 `{ ok: true, diagram }` 或 `{ ok: false, issues }`；intent 仅含单弦设置、增改删横按、窗口设置等实际行为。issues 含现有错误文案及字符串/横按/字段定位，供两种编辑表面共用。现有 `validateChordDiagram(): string | null` 继续兼容，实施时将同一规则集中为结构化校验结果再由兼容入口取首条，避免双份规则。

多字段横按事务在此计算候选值、做冲突检查、成功后一次返回。UI 的非法表单中间值保留在 local buffer；不得用“先改 strings、后改 barres”两次 onChange 制造可观察的半成品。Module 不管理 React、localStorage、音乐主历史或 Modal。

### 3.4 Chord preferences Module：本地配置事务

拟放在 `apps/website/components/EditorShell/chord-preferences.ts`，提供 `load`、`save`、`parseImport`、`export` 与订阅状态。Seam 放在存储读写处，注入浏览器 storage Adapter；另有会话内存 Adapter，用于不可用降级与测试。目录查询和图编辑是纯运算，无需为假想后端增加可替换层。

### 3.5 Score tonality Module：已提交曲谱的唯一推荐上下文

拟在核心新增 `score-tonality.ts`，Interface 为纯读取 `readScoreTonality(document)`，集中解析、拼写、音级比较、简谱记法验证与状态判别；歌曲设置、两个 Dropdown 和完整库共用，不在各表面复制判断。当前 Runtime 的已提交 `document` 是唯一事实来源，不能从和弦名、用户偏好、library 临时调性或未提交的歌曲设置草稿反推。

正式持久化扩展建议如下（类型示意；`SpelledTonic` 是经过语法和音级校验的主音拼写）：

```ts
type ScoreTonalityV1 =
  | { version: 1; tonic: SpelledTonic; mode: "major" }
  | { version: 1; tonic: SpelledTonic; mode: "minor"; minorTonicDegree: 1 | 6 };
// score.meta['lxm:tonality']?: ScoreTonalityV1
```

`tonic` 保留 `C / F# / Gb / Bbb` 等主音拼写，用于标题和调内和弦拼写；`tonicPc` 由它计算，不能作为第二份持久化事实。拼写比较和音级比较分开：F# 与 Gb 音级相同但呈现不同，关系校验按 pc，保存/撤销需保留用户选定的拼写。`keySignature` 继续使用现有 12 个值表示数字 1，不能据它推断大小调。计算出的数字 1 需映射到现有枚举的对应音级拼写，不能把超出枚举的 B# 等直接写入 `keySignature`。

- 大调主音为 1：`pc(keySignature) = pc(tonic)`。
- 小调必须显式记录 `minorTonicDegree`。普通小调在设置中建议“主音记作 6”，须由用户应用后才落盘；可显式选择“主音记作 1”。读入缺少该字段的小调资料时禁止补默认或猜测。
- 小调主音记作 6 时：`pc(keySignature) = (pc(tonic) + 3) % 12`，例如 A 小调、6 记法对应 `1=C`；主音记作 1 时为 `pc(keySignature) = pc(tonic)`，例如 A 小调、1 记法对应 `1=A`。两种记法都推荐 A 小调，不能把 `1=C` 误当 C 大调。

reader 返回以 `kind` 判别的联合类型，只有 confirmed 分支提供可用于“本调推荐”的上下文；其他分支提供显示状态与可定位原因，不伪造默认 key：

- `confirmed`：扩展结构、version、mode、拼写、小调记法均合法，且与非空 `keySignature` 的音级关系一致。标题如“曲谱 C大调”或“曲谱 A小调”。
- `unconfirmed`：namespace 不存在，但 `keySignature` 有值。标题固定为“曲谱 1=G · 大小调未确认”等，不能展示“G大调常用”。
- `unset`：namespace 不存在且 `keySignature` 为 null。标题“曲谱调性未设置”。
- `invalid`：namespace 存在但格式错误，例如 null/数组、无合法 version、缺 mode、无效拼写或小调缺 `minorTonicDegree`。标题“曲谱调性资料无效”，定位原因供设置修复。
- `unsupported`：可识别 version 为未知版本。标题“曲谱调性版本暂不支持”，保留原扩展，不能降级当 v1、默认大调或自动覆盖。
- `conflict`：扩展本身为合法 v1，但与 `keySignature` 不匹配；`keySignature` 为 null 也属于资料不完整的冲突。标题“曲谱调性信息冲突”，必须修正，不能只信其中一个字段生成推荐。

判别顺序先检查 namespace 是否存在，再判扩展版本与结构，最后校验与 `keySignature` 的关系。无可识别 version 属 invalid，明确未知整数版本属 unsupported。上述后五类均暂停本调推荐，保留全部和弦搜索、“我的常用”、完整库查看和设置入口；错误不阻止打开谱或丢弃未知 meta。只有 namespace 不存在才使用 unconfirmed/unset，不能把坏扩展冒充“尚未设置”。

两处 Dropdown 即时订阅同一 Runtime 已提交 document 的变化，切谱、文件替换、undo/redo 和成功应用曲谱信息均重新读取；不能只在首次 open 缓存，也不能只按可能回退的 documentRevision 判断。任何旧推荐查询/异步结果携带会话与 stateVersion，变化后丢弃。歌曲设置中的 mode/主音编辑只影响设置预览，应用前两个 Dropdown 仍读旧的已提交状态。读取本身不写 document 或用户配置。

schema 4–8 缺 mode 的旧谱不自动猜大调，也不因缺 mode 触发升级。4–7 如需使用现有显式升级流程，升级后仍保持“未确认/未设置”；不注入默认扩展。JSON 保存、加载与升级须保留 namespace 和其他未知 meta，未知/无效扩展可随文件原样往返，不为推荐失败删除数据。

### 3.6 Score info command Module：原子写入与设置草稿

本方案明确选择**新增 `SetScoreInfo`，保留 `SetNotationInfo` 兼容**，不串行发“改 key”和“写 meta”两条命令。新命令承接 title、arranger、keySignature，增加 typed `tonality?: ScoreTonalityV1 | null`：`undefined` 保留当前 namespace 原值，`null` 显式删除，仅合法 value 设置。命令不能接受并回写整个旧 meta 快照。

执行时从**执行当下**的 document 复制 score/meta，只改 `lxm:tonality`，保留其他 namespace；先规范化文本、验证输入，再一次 finalize。设置 value 或变更 key 时必须校验候选 `keySignature` 关系；只编辑标题/作者且 preserve 旧资料的例外见下段。value 合法但 key 不匹配或为空时整体拒绝，不静默修正调用方的矛盾输入；设置表面应先根据记法计算预览和待提交 key。相同文本、key、扩展内容为 no-op，不增 revision/stateVersion/历史；实际修改只产生一次历史，一次 undo/redo 同时恢复 title、arranger、key 与扩展。拼写改变即使 pc 相同也属于真实修改。

兼容 `SetNotationInfo` 仍不改 meta：若它确实改变 `keySignature`，且现有扩展本身为合法 v1、与候选 key 不一致（包括改为 null），拒绝并提示改用 `SetScoreInfo` 成组修改。若 key 未变，允许正常编辑标题/作者，不能被原有未知、无效或冲突 meta 卡住；不修改或“修复”这些数据。`SetScoreInfo` 的 undefined 同样允许不改 key 的标题编辑并保留坏/未知扩展；改变 key 时若保留的是未知或无效扩展，需显式修复或删除 namespace，不以标题提交顺带覆盖它。无扩展的旧谱仍允许仅改 `1=`，状态维持 unconfirmed。

歌曲信息设置在现有 info 组加入主音、mode、小调记法及扩展原值/读状态；保持一个 info 草稿和一次“应用曲谱信息”。展示数字 1 的同步预览：大调为主音，小调按已选 1/6 计算；已有仅 `1=…` 的旧谱显示“大小调未确认”，不得预选大调当成已确认。对未确认旧谱选择 mode/主音时可给建议，用户应用才保存；未知/无效/冲突资料提供显式修复或清除操作，标题编辑默认 preserve。清除调性资料时删除 namespace，是否保留 `1=` 由设置明确展示，保留则回到 unconfirmed，两者都清空则 unset。

info 组整体处理 dirty、reconcile 与提交冲突，特别是 key、tonic、mode、minorTonicDegree 不能逐字段 rebase：干净组随已提交文档刷新；dirty 组遇到该组任一外部变化，保留整组用户值和旧基线，提示恢复本组或核对整组后重试，不能混合成“旧 mode + 新 key”。基线包含原 namespace，以捕获未知值变化；其他 namespace 的变化不算此组冲突，提交时从最新 meta 保留。提交前检查 session/stateVersion 和组基线，失败不产生部分修改。曲谱信息这一次 apply 仅发一条 `SetScoreInfo`，不顺带提交 capo、拍号等其他组。

info 草稿使用明确的写入意图 `preserve | delete | set(value)`，与基线 `{ namespacePresent, namespaceRaw, title, arranger, keySignature }` 分开；原 namespace 是否存在与其值为 null 不能混为一谈。raw 取独立快照，按 JSON 内容语义比较（对象键序不影响相等，数组顺序有意义），不用对象引用 `!==`；reader 的状态/错误是派生值，不作为 dirty 字段。`preserve` 编译为命令字段 undefined，`delete` 为 null，`set` 为合法 value；等值 set 与未改文本不造成假 dirty。同步改造 `planSettingsCommands`、`commandGroups`、提交预验证与错误归组，使 `SetScoreInfo` 全程归 info，一次组提交只生成一条该命令。

现有 `ScoreSettings.update` 在冲突后编辑任一字段就刷新整组 initial 并清冲突（源码第 164–176 行），必须同时改造：普通输入包括仅改标题不能解除 info 冲突。提供“加载已应用信息”和“核对并保留整组输入”两个内联操作；后者展示新旧组差异，用户操作时绑定最新组快照并重新验证全部关系，才更新基线并解除冲突。提交前基线再次变化则重新冲突，不能一次确认后永久认可后续变化。其他设置组维持既有行为，不借此重写整套设置。

应用只更新曲谱信息和谱首 `1=` 显示，不转置已有音符或和弦，不改名、不平移指法。取消/恢复未应用设置不改变 document 或和弦父草稿。主音拼写与 capo 的指型语义在设置中说明，不在小型 popup 标题堆放技术说明。

### 3.7 Catalog resource Module：HTTP 获取与目录快照

拟在网站新增 `chord-catalog-resource.ts`，由 Runtime 接入共享资源状态，向两个入口和库提供同一份不可变目录快照。Interface 收拢 `ensureLoaded()`、`retry()` 与可订阅状态；fetch 与超时由依赖注入，核心只接收已解析的数据。无需为对象存储再建一套业务后端或上传管理系统。

资源状态区分 idle/loading/ready/error；保留已有快照时可附带刷新失败状态。首次进入和弦编辑时触发加载，同源同入口的并发请求复用同一个进行中请求；输入搜索、切调性、切指法都在已加载目录中本地完成，不逐按键发 HTTP。不在模块初始化或 SSR render 中发请求。

目录载入按 manifest 获取、格式版本检查、数据获取、完整校验、一次发布快照的顺序进行。HTTP 非成功状态、超时、非 JSON、未知格式版本、manifest/dataVersion 不匹配及结构/引用错误都进入明确失败状态，不发布半张库、不悄悄跳过坏项冒充完整覆盖。两次请求共用 10 秒总时限，manifest 上限 16 KiB、catalog 上限 2 MiB；读取响应流时累计字节并超限中止，不仅依赖 Content-Length 或读完整个 JSON 后再检查。手动重试复用当前进行中的加载，不产生并行重试风暴；结束或超时均释放进行中状态，重试使用新的 AbortController 和请求序号，已超时/被替代请求的迟到结果不得发布或清掉新请求状态。

当前会话已经有完整合法快照时，刷新失败继续使用该快照，并提示“更新失败，继续使用已加载的和弦库”；首载失败则禁用依赖系统库的选择，提供“重试”，已保存和弦的显示、名称编辑、自定义指法和独立用户收藏仍可工作。系统快捷引用暂不可用时保留其配置，不删除或替换。用户收藏直接读取自己的完整快照，不要求先成功拉取系统目录。

本期缓存采用浏览器 HTTP 缓存加应用会话内快照，不增加 IndexedDB、Service Worker 或离线同步。浏览器已有缓存可能支持复用，但不能承诺首次离线或刷新后的离线可用。资源请求的生命周期与某个 Beat 分开：切目标不会将公开目录写入音乐草稿，重建 Runtime 时旧订阅失效；不为同一资源的每个视图重复获取。运行中的 Modal 有合法目录时固定该快照；若打开时尚未加载，允许同一次有效请求的首个合法快照进入，进入后固定版本。用户在失败 Modal 中重试成功也适用此规则，不能因“打开时没有快照”永久锁死。已有版本的 Modal 不热切库，可关闭重开使用新版本。用户收藏独立于系统快照可用。完成仍校验曲谱目标 token，目录加载完成也不得自动选择、覆盖父草稿或把旧目标的选择回填到新拍。

加载/失败提示放在两处“我的常用”和 Dropdown 的系统候选区、完整库的系统浏览区；保留当前名称、已有指法预览、自定义入口、我的指法和常用配置入口。加载中显示“和弦库加载中…”，重试按钮禁用；首载失败显示“和弦库暂不可用”及重试，曲谱调性来源仍照常显示，不能把网络错误显示成“调性未确认”。刷新失败有旧快照时显示保留版本的提示并继续选用。只有 ready 后确实查不到引用，才标“该预置已移除”；加载中/首载失败显示“等待和弦库/暂不可用”，不当作配置损坏。对应[故障与配置状态稿](../prototypes/chord-library/failure-states.html)仅模拟状态，不发送真实库请求。

## 4. 入口、目录与选择行为

两处快捷栏标为**“我的常用”**，最多六项，共用 `{ identityId, defaultVoicingId }` 的有序列表，默认仍是 C/G/Am/F/Dm/Em。它是全局用户配置，切谱或改调不自动改顺序/内容；不得标成“本调常用”。本调推荐只出现在 Dropdown 的推荐区（完整库可按调性浏览）。一个系统 identity 只占一个快捷位，切换默认 voicing 不新增重复项。自定义收藏使用 `user:<uuid>` 作为独立身份并关联其 voicing，避免把自由名称强行映射为系统身份；不计入 192 个系统 identities。

快捷按钮名称可换行；“更多 ⌄”为固定、不收缩的独立按钮，始终可见。布局允许快捷项区域换行，不能让按钮被横向裁掉。选择第七个候选时提示已达上限并定位配置列表，不自动移除原项。0 项时仅保留“更多 ⌄”。“更多”只表达展开状态 `aria-expanded`，不作为选中和弦按钮，不被和弦名称替换。

Dropdown 包含搜索输入、曲谱来源标题、本调推荐、完整库和配置入口。标题始终来自第 3.5 节 reader；confirmed 时可显示“曲谱 C大调 · 本调推荐”，不得因当前和弦叫 G、临时浏览 G 或偏好导入而变成 G 大调。无查询默认只列该调自然调内三和弦/七和弦，小调和声补充单独标组。C 大调对应 `C Dm Em F G Am Bdim` 和 `Cmaj7 Dm7 Em7 Fmaj7 G7 Am7 Bm7b5`；D、A、Bm、D7 等不能混入未注明的“C大调常用”。本期不新增借用/次属推荐来解释这些候选。

搜索匹配全库 canonical name/alias，不受本调限制；输入 C# 和 Db 可命中同一项，结果显示对应拼写，区域另标**“全部和弦搜索结果”**。先解析根音，再按显式 alias 匹配性质，不能把整串统一转小写：`CM/CM7` 的大调别名和 `Cm/Cm7` 的小调含义不同。规范化 ♯/♭ 与首字母大小写不抹平性质；未识别的自由名称不自动修正。曲谱来源标题保留，不能将非调内搜索结果挂在“本调推荐”下。清空搜索恢复推荐或对应暂停状态，空结果给清空/返回路径。

入口由“切换调性”改为**“设置曲谱调性”**，明确打开歌曲信息设置并聚焦调性组，不能在 Dropdown 旁路修改推荐 context。设置输入仅形成 draft；一次“应用曲谱信息”成功后真正改曲谱，两个 Dropdown 同步刷新；取消则推荐和和弦草稿均不变。打开设置时的 owner/焦点约束见第 7 节。

完整库分“按调性／全部／我的指法／常用配置”。每次 open 默认**“跟随曲谱”**，读取当前 reader；没有 confirmed 时暂停跟随推荐并提供设置入口，仍可搜索、全部浏览及查看我的指法。用户可在库内显式选择临时主音与 mode，此时横幅如**“临时浏览 G大调 · 曲谱仍 C大调”**并有“返回本曲谱”；若谱未确认/无效，横幅第二段使用 reader 的真实状态。曲谱来源标签仍显示当前已提交状态，临时选择不能回写它。

“全部”的根音只过滤 identity；“按调性”的临时主音/mode 只控制库内浏览，均不改 key、meta、capo、音符或已有和弦，不回写配置。关闭后丢弃临时状态，下次 open 重置跟随，不使用 `lastKey`。同会话 undo/redo 或曲谱调性变化即时刷新跟随结果/来源标签，清理过期选择；切谱则关闭旧选择事务，新谱重开继续默认跟随。若变化使 Modal token 过期，按第 7 节失效关闭，不以重新渲染标题绕过回填校验。

可查看的 identity 不等于可选用的 shape。无审核通过指法、图缺失/不合格或调弦不适用时，**快捷项/Dropdown 的选用动作及“选用此指法”预先 disabled 并有内联原因**；保留独立“查看详情”路径，可访问名称、说明和示例。不能先启用按钮，点击后才用 toast 告知没有图。库可聚焦 identity 查看详情，但该操作不回填父草稿，取消也不改变父值；原型也须表达相同可用性。

库内点击和弦及 voicing 只改变库的选择副本，右侧显示完整名称、指法、位置、禁奏/空弦和指型标签。点“选用此指法”才一次回填父草稿的名称和完整图，保留父 display；取消整个库，父草稿保持进入前值。快捷项、Dropdown 直接选项同样一次替换名称和图，保留 display。纯改名称始终保图；清图才按现有契约切到 `name`。若新建草稿当前为“仅名称”，选图后仍为仅名称，并显示“指法已保留，谱面当前仅显示名称”，让用户显式选择是否显示图。

选中的系统/用户图每次深拷贝，既不与系统目录、收藏也不与其他谱面标记共享可变数组。最终 `SetChordSymbol` 只包含现有 `{ name, diagram, display }`；库更新、收藏修改或删除不能追改已保存谱快照。

## 5. 系统目录的和声与指法审核

### 5.1 调式拼写与 aliases

推荐先按调式的音阶级数字母求拼写，再映射音级 identity；不能全局 `replace(Gb, F#)` 后拿升号表替代所有调性。支持 `B# / E# / Cb / Fb` 等别名，理论调性需要时支持重升/重降拼写；查询匹配和目录计数仍按音级归一。

例如 Gb 大调保留 Cb；若用户明确选择 Gb 小调，其自然音阶应按 `Gb Ab Bbb Cb Db Ebb Fb` 拼写。可另给“等音 F# 小调”可选入口，但不可在 Gb 小调标题下直接展示 F# 小调拼写。自然小调三和弦级数为 `i ii° III iv v VI VII`，七和弦为 `i7 iiø7 IIImaj7 iv7 v7 VImaj7 VII7`；和声小调常用补充单列，不覆盖自然小调推荐。大调对应 `I ii iii IV V vi vii°` 及 `Imaj7 ii7 iii7 IVmaj7 V7 vi7 viiø7`。

调性拼写并不要求把系统库复制成多个等音条目。和弦品质别名可收录 `M/maj`、`ø/m7b5` 等，但只接受明确约定，不把任意自由名称“修正”为系统名字。

### 5.2 可交付数据门槛

不能通过把开放和弦所有 fret 加半音盲目生成 192 项。仅以明确可移动的封闭 shape 为候选源，并同步审核禁奏、最低发声音、横按、起始品和跨度；开放弦的处理必须有具体设计和证据。每个 shape 上线前经过下列审核：

1. **结构**：现有 schema 和统一图校验均通过，1→6 保存、可空手指、显式横按、固定五格协议。
2. **和声**：标准调弦 MIDI 加实际 fret 得到每根发声弦的音，保留真实最低音和音程，再比较该 quality 的 expected formula；不以名称匹配或包含根音作为全部证据。
3. **低音**：本期每个 identity 至少一个根音低音版本；其他审核通过的转位需明确 bass 标签，不在未声明时混入根音版本。slash 全覆盖不在本期要求内。
4. **演奏性**：跨度、实际手指分配、横按冲突、常见手型与必要伸展审核。五格合法并不等于可弹；审核者与理由记在目录数据/审核记录中，自动校验负责可计算事实，人工负责可弹奏性确认。

formula 是 quality 的显式规则：major `[0,4,7]`、m `[0,3,7]`、7 `[0,4,7,10]`、maj7 `[0,4,7,11]`、m7 `[0,3,7,10]`、dim `[0,3,6]`、dim7 `[0,3,6,9]`、m7b5 `[0,3,6,10]`、aug `[0,4,8]`、sus2 `[0,2,7]`、sus4 `[0,5,7]`、add9 `[0,4,7,14]`、6 `[0,4,7,9]`、m6 `[0,3,7,9]`、9 `[0,4,7,10,14]`、m9 `[0,3,7,10,14]`。9 和 m9 明确允许省略五度，仍须有根音、三度、七度和九度音级；其他省略若要支持必须逐性质显式定义。本期不把无根音爵士指法算作基本覆盖。

允许同音八度重复，匹配 pitch class 时仍记录扩展音和实际排列，审核确认九度、低音及指型合理。不得用“所有公式必须逐音齐全”误拒合理九和弦，也不得用“任意少一个音都允许”误收缺三度/七度的形状。`validateChordDiagram` 对用户图继续只做结构校验，用户自由名称与图的和声一致性不成为保存硬门槛。

交付时生成覆盖清单：192 identities 的数目、每个合格 voicing 数、aliases 不重复计数、未审核/失败项和原因。热门 2–3 个版本的名单在阶段 2 数据评审时列定，不能仅增加重复指法凑数。

### 5.3 调弦和 capo 文案

系统候选基于标准调弦 E A D G B E。将当前两处 gate 收敛成共享判断，按弦号、pitch 和对应 MIDI 核验；与标准常量不一致即暂停系统指法选用。非标准调弦仍可搜索查看系统示例、改自由名称、编辑/收藏自定义图，但明确系统图仅供标准调弦，不允许误回填。已有图保留。

capo 维持现有指型名称语义：例如 capo 2 的 C 指型仍叫 C，不自动改写为 D，也不根据库筛选改变 capo。曲谱调性在此推荐流程按指型/记谱上下文使用，不能随 capo 自动加半音变成实音调；设置中说明“指法与名称按当前指型记载；变调夹不自动改名或转调”。小型 popup header 仅展示曲谱状态，无需塞入这些解释。本期不推导和保存实音和弦名，系统 shape 的音程审核以无 capo 标准调弦为基准；这不改变相对 capo 的谱面品位协议。

### 5.4 项目内 JSON、同源 HTTP 与版本管理

系统预置数据、用户偏好配置和谱文件是三种不同资源。HTTP 只获取公开只读的系统库；用户常用/收藏仍按第 6 节在本机保存，曲谱调性仍归谱文档。系统 JSON 不携带“当前曲谱调性”，推荐根据当前已提交曲谱与目录动态计算，不为 24 个大小调重复存储整套指法。

使用项目内的小型 manifest 指向不可变版本的数据文件。仓库路径为 `apps/website/public/assets/chords/manifest.json` 与 `apps/website/public/assets/chords/catalog-2026.11.07.1.json`；浏览器通过 `/assets/chords/manifest.json` 读取，`public` 不写进请求地址。开发和部署均由现有 Next.js 静态资源机制提供，不新增 API route、存储 SDK、后台服务或外部网络依赖。以下是格式示例，数据文件中的单个 C 和弦仅用于说明字段，**不是完整发布库**：


`formatVersion` 表示 JSON 协议版本，`dataVersion` 表示内容发布版本，两者均独立于谱 schema v8 和用户配置 version 1。首期 `guitar-standard` 只映射核心已知的六弦标准调弦常量；客户端不因远端添加未知 tuningId 或 quality 就自动接受新音乐语义。identity/voicing id 在内容版本间保持稳定，不能拿旧 id 重新代表另一种和弦/指法。

客户端严格验证必填字段、唯一 id、根音与性质、别名、默认指法引用、图结构、调弦及版本一致性；identity id 必须与 rootPc/quality 一致，同一 identity 内 voicing id 唯一，跨 identity 的引用使用二元组。alias 解析后不得冲突地指向不同 identity。发布前校验另外执行第 5.2 节的公式/低音、192 项覆盖和人工演奏性审核；审核记录单独放 design-v2 验收资料，以 identity/voicing/dataVersion 关联，本期运行时 JSON 不必承载审核者资料。远端来源不降低审核标准。已发出的版本文件保持不可变；更正数据发布新文件与 dataVersion，不原位改写同名版本。

本期只使用项目内的同源 manifest 地址 `/assets/chords/manifest.json`，集中在资源 Module 管理，不新增第三方地址配置或对象存储环境变量。`catalogUrl` 相对于实际 manifest 响应 URL 解析，不能相对于当前页面路由解析；解析后必须仍是网站同源的 chords 静态目录内 JSON，拒绝外部 URL、越出资源目录及跳转到外源的响应，避免配置文件意外引入外部依赖。若网站现有部署使用子路径，复用已有 basePath 规则。未来迁移对象存储时再扩展资源地址配置，不改和弦 JSON 结构与编辑逻辑。

manifest 请求使用 `cache: "no-cache"`，让浏览器重新验证；版本数据文件可正常复用 HTTP 缓存。若生产部署已支持资源响应头，可将 manifest 设为 `Cache-Control: no-cache`、不可变版本文件设为长期缓存；不为此引入新部署服务或保证现有托管尚未配置的缓存头。每个应用会话首次加载或显式重试检查 manifest，成功后复用会话快照，不定时轮询或在编辑中强制热切库。本期数据与 manifest 一起随项目发布；构建/部署前验证两者匹配且版本文件存在，更新保留旧版本文件，回滚还原指针与项目版本。客户端会话中的已打开编辑事务仍使用其原快照。

本期资源与网站同源，没有对象存储账号、bucket、CDN、密钥、跨域 CORS 或上传界面接入。未来若迁移，再处理外部 HTTPS 地址、响应头、CORS 及“先上传版本文件再更新 manifest”的发布流程，均不作为本轮验收要求。同协议的数据更新只改 JSON 资源，不需要修改和弦 UI；新增客户端不认识的性质/协议则仍需相应代码升级。

库版本更新、删除目录项或加载失败均不改变已经写入谱面的名称与完整指法快照；常用配置失效引用按第 6 节标明，不能自动指向别的指法。本期不提供运行时切换 manifest 来源；未来扩展该能力时再增加按来源区分缓存及旧请求失效处理。

## 6. 本地配置与 JSON 契约

独立 storage key 建议为 `lxm.chord-preferences.v1`，内容 `version: 1`。它不是谱文件，也不改变谱 schema v8；正式曲谱调性只在第 3.5 节的谱 meta 中持久化，不写入本配置。建议单文件数据形态（Interface 示意）：

```ts
type ChordPreferencesV1 = {
  format: "lxm-chord-preferences";
  version: 1;
  revision: string; // 用于跨标签检测，并非谱 documentRevision
  quickItems: { identityId: string; defaultVoicingId: string }[]; // 0–6
  customVoicings: {
    id: string; // user:<uuid> 身份，及稳定 voicing id
    voicingId: string;
    name: string;
    diagram: ILXMChordDiagram;
    tuning: { pitch: string; midi: number }[]; // 1→6
  }[]; // 建议上限 200 个收藏
};
```

系统库不复制进配置，只保存稳定引用；用户图保存完整快照和其适用调弦。用户收藏在标准调弦下可和系统 identity 关联展示，非标准调弦收藏仅在调弦一致时允许选用；其自由名字不代表系统身份。编辑系统指法另存为用户副本，不覆写系统库。“存入我的指法”是显式配置写入，与“完成编辑”和“应用到谱面”分开，不暗中同步三个层次。

配置无 `lastKey`、mode 默认值或推荐调性字段；不记录 library 临时浏览。配置导入只可替换我的常用/收藏，不能调用曲谱命令、改 meta 或改变本调推荐上下文；文件中夹带曲谱调性字段按未知字段报告，不能解释为设置曲谱。切谱或改调也不自动改 quickItems。未实施过的旧提案 `lastKey` 不形成需要兼容的已发布格式。

导入的系统引用按 identity/voicing 二元组校验格式，尚未载入目录或当前版本找不到的引用作为“待解析/不可用”保留并列入预览，不等同坏图或自动删除；用户收藏引用必须能解析到同文件中的合法收藏，否则整份导入失败。用户收藏以 id 区分，即使同名也能分别查看、选用和删除。导入预览记录当前配置 revision；确认替换时再次校验 revision 与文件结果，外部变化走冲突流程，不能用旧预览覆盖新配置。配置 revision 由本机成功保存时新建，不采信导入文件带来的 revision。

配置页有独立配置草稿，保存后两处快捷栏立即共用；关闭未保存的配置页丢弃配置草稿，音乐父草稿不变。上限 200 建议作为初期可审查的产品容量，超限阻止新增/导入，提供定位和导出清理路径，不截断用户记录。输入文件先检查格式、版本、体积（建议 1 MiB 上限）、字段、200/6 上限、去重、引用和每张图；确认替换前展示有效项、冲突、坏项及前后数量。初期只做“替换本地配置”，不做隐式合并、自动改名或删除重号用户项；有坏项时禁止正式替换，允许导出问题报告供修复。解析和预览不写 storage。

本地已有坏数据读取时隔离：保留原始备份或提供可下载的原始记录；有效收藏可加载，无效记录进入隔离列表并说明原因；缺失引用的快捷项禁用并标出，不能偷偷改成别的图。若保存会丢掉隔离项，要求先在配置页显式处理后才能替换；不另弹确认 Modal。未知新版本不覆盖原值，以默认配置或内存会话运行并提示版本不支持。

SSR 不在模块初始化/render 阶段读取 `window/localStorage`，先给稳定默认值，再在客户端 effect 加载；严格校验后发布共享状态，避免两表面各自 hydration 读取。所有读写、JSON 和订阅失败均捕获：保存失败可以保留当前会话配置，但返回 `persistence: "memory"`，提示“本次会话可用，未保存到浏览器”；不能显示“已保存”。降级不写空对象覆盖原数据，保留导出能力。写入成功后才更新持久化 revision 和显示“已保存到此浏览器”。

同标签使用同一订阅源，不能指望 storage event 通知自己。跨标签收到 storage event：无配置编辑时先验证再同步；有未保存配置草稿时保留本地草稿，显示“其他标签已更新”及加载外部/保留本地两个内联操作；保存前重读 revision，发现不一致则拒绝静默覆盖。保留本地是用户明确选择后基于最新 revision 重新保存。localStorage 无跨标签比较并交换事务：极近同时写入仍以浏览器最后写入为准，随后读取/事件检测不一致并提示冲突，不声称强一致。此类配置更新不得改变正在编辑的音乐父草稿或 custom buffer；引用被删除时完成回填仍以打开时独立快照为准。

### 6.1 不同保存动作的交互约定

清除已确认调性同其他设置一样，先形成设置草稿和预览；“应用曲谱信息”才删除 namespace，取消保留原调性。未知版本资料的修复/清除必须由用户显式操作进入待应用状态，不因打开设置自动变为 v1。图形编辑的“存入我的指法”则为即时独立配置保存，取消 local 不撤回已保存收藏，按钮附近说明该差别。

## 7. Modal 会话、竞态与提交

### 7.1 打开与互斥

从 popover 点击“更多→库/配置”或“编辑指法”时，先捕获同一 owner/token/目标/版本/父草稿基线，再关闭 Dropdown 和隐藏 popover；隐藏不调用 `returnToScore`、`perform(close)` 或失效 owner。通过 Runtime Modal controller 打开唯一主 Modal；已有其他主 Modal 时不覆盖它，返回 blocked 并保留草稿。不能另建不受控制器管理的 AntD Modal 绕开互斥。

扩展 Modal request 的和弦类型及 `EditorModalHost` 呈现，沿用 busy、isValid、version、onClose、afterClose、restoreFocus。背景侧栏、popover、谱面和提交/输出快捷键受同一 busy/Modal gate 阻止；不能只遮住视觉区域却让背景操作改变目标。Modal 内的下拉不是第二个主 Modal。

现有控制器 `close` 立即清 current，只有 `resolved` 会保留 afterClose；普通 `cancel` 不执行交接。因此不能只在库的取消回调里串开 custom。扩展受控 `handoff(id, next)` 语义与按 request id 管理的 closing/pending-transition 状态；该关闭只丢弃库选择副本，不等于写父草稿或提交谱面。退出动画期间 `isOpen()`/统一交互 gate 持续占用，宿主收到对应 afterClose 后同步校验并原子交接下一表面，期间不恢复背景焦点、不允许普通 open 插入。真正 cancel/stale 则在动画结束释放并按规则恢复焦点，不执行待转场。迟到旧 afterClose 以 id 判别，不能释放新任务的锁。既有结构、粘贴、技巧 Modal 的 resolved/cancel 行为必须保持，并纳入回归。

每次完成回填前同步核对 token、owner generation、session version、document/stateVersion、目标仍可解析及父草稿基线；任一不一致则以 stale 关闭并提示“原编辑目标已变化，请重新打开”，不向新拍回填。文件替换/会话重建、撤销重做、删除原 Beat、目标切换和异步导入迟到回调都走此路径。通常背景被锁不会发生变化，但仍必须保留验证。旧任务关闭后不得清除新任务状态。

### 7.2 从库转自定义

库中“基于此指法自定义”先取**库选择副本**作为 seed，关闭库并在 afterClose 有效性检查后打开 custom；保持原 owner/token 的目标身份，生成新的表面 request id 防止库迟到回调。关闭动画期间不把焦点还给背景，不允许两个主 Modal 同时存在。

转场**不先覆盖父 draft**。custom 取消丢弃 local buffer，恢复进入库前的父草稿；默认回到原编辑入口，不自动重开库。custom 完成才将当前名称与完整图一次回填父草稿，并保留原 display。独立“存入我的指法”只写用户配置，不把未完成值回填谱面；若用户已显式保存收藏，随后取消 custom 不回滚该已保存配置，界面需说明两者作用。

### 7.3 草稿和历史

三个层次清楚分开：谱面已提交快照、Sidebar 父草稿、custom local buffer。库选择副本和配置草稿也各自独立。custom 的“完成”只回填父草稿，不发领域命令；父“应用和弦”沿用一次 `SetChordSymbol`、一次主历史记录。取消/关闭 custom 丢掉 local，但不恢复或丢弃父草稿先前已有的修改。

local buffer 的撤销/重做仅作用于本次图编辑，名称、窗口和一次多字段横按也各是一条局部操作。完成后丢弃局部历史；主撤销只在谱应用后恢复上一完整和弦。输入框内原生文字撤销保留，不劫持成谱面撤销；非输入编辑区 Cmd/Ctrl+Z 才进入局部历史。Modal 开着时不透传主撤销。

将 Modal 活动/未完成 local 状态纳入同 owner 的草稿登记与输出闸门；当前 canApply 为 false，focus 指向 Modal，不能只登记父草稿的合法值而让输出流程漏掉 local 修改。[协调器 Interface](../../../apps/website/components/EditorShell/editor-draft-coordinator.ts#L30)可以承载该状态。无须新建第二个可同时提交的 owner；关闭 local 后恢复父草稿登记。

### 7.4 设置曲谱调性的交接

Dropdown 的“设置曲谱调性”关闭菜单并通过专用 suspend/resume 交接到现有歌曲信息设置。同一 owner 下保留和弦父 draft、initial、原目标、owner 身份、document/stateVersion 和恢复焦点信息；不得为导航自动应用、丢弃或清空和弦草稿。现有 settings focus 会进入普通 `request(tab)`，随后失效 owner 并清草稿（`MusicTextSidebar` 第 1560、588、692 行），本入口明确禁止直接调用该普通路径；普通用户主动切栏目仍沿用已发布的丢弃规则，不全局改变它。

歌曲信息设置草稿独立登记；暂停的和弦草稿仍登记 dirty、不可应用，输出闸门同时识别两者，不能通过暂时隐藏绕过未应用检查。未应用的设置不触发曲谱订阅。返回按钮明确“返回和弦编辑”；设置有未提交信息时沿用现有 settings 离开处理，取消返回动作仍留在设置，放弃设置输入才恢复和弦。若从完整库进入设置，丢弃库选择副本并使用第 7.1 节 handoff 关闭/交接，不能用控制器普通 cancel 期待 afterClose，不能叠加第二个主 Modal 或沿用库回填 token。此交接仅开放设置表面，原和弦目标保持暂停；应用/导出及其余谱面快捷操作仍走既有 gate。

取消设置时恢复原和弦父值和目标，不发任何领域命令；再次打开“更多”仍显示原已提交曲谱状态。应用设置成功仅执行一条 `SetScoreInfo` 并同步两入口；和弦父草稿的名称、图和 display 保留，不顺带应用。因该命令产生了新 document/stateVersion，旧库/custom 请求 token 全部失效，不得直接沿用；恢复和弦编辑前重新解析同一目标、读取其已提交和弦基线，确认只发生该次已知信息提交且和弦基线未变后，为保留的父草稿建立新版本登记。若期间有其他编辑、切谱或目标失效，走既有 stale/离开处理，不能把旧 draft 挂到新谱。

正常背景 gate 仍阻止其他谱面编辑。设置的 dirty 组如遇外部更新按第 3.6 节整组冲突处理；关闭未提交设置不回滚已经应用的设置，和弦草稿取消也不回滚已提交曲谱信息。该交接在实施中需验证协调器的登记/输出闸门，不以隐藏和弦表面等同离开 owner。

## 8. 图形编辑规则

### 8.1 网格和精细字段

视觉从左到右 6→1 弦，数据始终 1→6；每个点击目标有弦号/品位可访问名称。弦顶明确 0/× 选项，按品格选定该弦唯一 fret；手指默认可为 null，不强迫逐弦填写。原有六弦品位/手指表与网格操作同一 local buffer，不持有各自的图。

按弦、横按、擦除工具有明确模式。横按依次点同一品位的两个不同弦端点即可，无必需拖动；第一个端点仅是待定 UI 状态，不改图；Escape 取消待定端点。表单可直接填写品位、起弦、止弦和手指完成同一事务，内部将两端按 `minString < maxString` 规范化，不改变 UI 的 6→1 阅读顺序。单弦设置若破坏已有横按解释，提供相关横按定位，要求在同一图中修复，不能静默删横按。

起始品是观察窗口，调整它不平移任何 fret。谱协议保持 `fretCount: 5`，渲染可依现有规则收缩为 3–5 格。窗口外按点提示弦号和实际品位，提供窗口调整路径；跨度本身超五格则说明不能仅靠移窗口修复。

### 8.2 横按的原子事务

添加/修改横按时在候选副本完成所有同步，再校验，再一次写回 local buffer：

1. 覆盖区内的 0、× 或低于目标横按品的弦，提升到横按品；等于横按品的弦也建立该横按的手指解释。对应 finger 设为横按 finger。
2. 覆盖区高于横按品的按弦保留实际 fret 与原手指；若该手指与横按 finger 冲突，拒绝整个操作并定位，不静默清除高品指法。
3. 重复使用同一 finger 的第二条横按、同品位重叠、与其他手指/横按冲突、超过四条、非法端点和无法容纳的跨度，都原子拒绝；原 strings/barres 不变，不加入撤销历史。可直接定位到冲突行和弦格修改，不加确认弹框。
4. 若待覆盖的弦已属另一条横按或存在其他冲突，不能为新横按偷偷删除旧横按或其手指；只允许该事务自身明确涉及的 strings 和当前横按变化，其他用户数据保留。

修改横按需要先在候选中移除该条旧描述，再按新范围/品位/finger 构造，不能按“新增第二条”检查同 finger。旧范围退出或换 finger 后失去解释的旧重复手指组，沿用删除规则仅清为 null、保留实际 fret；新覆盖区再按上面的规则同步，其他横按及其解释不动。缩范围、移范围、换 finger 各为一次可撤销事务；清理前后给出具体弦号。旧范围若与其他横按共同解释指法，不能清除仍被合法解释的部分。不同品位横按可覆盖同一根弦，只按实际 fret/finger 校验，不将“范围相交”一概拒绝；同品位范围重叠仍拒绝。

删除横按不改变六弦的实际品位。删除后若重复 finger 已失去显式解释，仅将因此失效的重复 finger 组清为 null，保留独立且合法的手指，并显示“已保留品位，相关重复手指改为未指定”。删除和这些必要清理是一条可撤销事务，一次撤销恢复横按和手指。擦除横按与表单删除同义，不把整片音静音。

### 8.3 非法中间态与预览

表单清空品位、超窗和其他非法输入可以保留在 local buffer，错误定位到具体字段。网格仍绘制可确定的部分，标出冲突/窗外信息，并允许点击修复；不把整个编辑网格因校验失败而隐藏。图预览与网格是不同输出：谱预览只使用最后一份完整合法快照，明确标记“显示上次有效指法；当前修改尚未通过校验”；从无合法图开始则显示空态。

父草稿若仍允许直接表单编辑，也采用最后合法快照输出，不能把 NaN 或冲突图传给布局。最终“完成”在名称/图非法、IME 组合中或 token 过期时禁用；父“应用和弦”沿用现有硬校验。`lastValid` 仅用于显示，不是失败时偷交旧值：用户点完成不得把旧图当作本次修改成功。

## 9. 键盘、焦点和低屏

Dropdown 打开后聚焦搜索；箭头移动候选，Enter 选择明确候选，Tab 可到完整库与配置，不触发父“应用”。IME composition 及已有 cooling 期间不消费 Enter/Escape 进行选择、完成、关闭或主命令；组合字落定后才恢复快捷键。

Escape 按最内层优先：先关 Select/Dropdown 并还焦点到其触发器；若没有内层 popup，再取消待定横按端点；再取消当前主 Modal；只有全部关闭后才由原和弦编辑表面处理 Escape。每层消费后阻止冒泡，不允许一次 Escape 连关多层或把父草稿丢掉。替换当前侧栏仅关旧预置菜单的 Escape 特判，纳入共同规则。

Modal 使用现有焦点圈定，标题/错误可读，打开 custom 后聚焦名称或首个可操作格；网格采用 roving tabindex，方向键换弦/品，Enter/Space 执行工具，且始终有普通表单替代。错误播报以实际变化为准，不能每次 render 重复宣读。关闭后优先还到原“更多 ⌄”/编辑指法按钮；原触发器隐藏时返回同目标可见入口，再退到谱面安全焦点。失效目标不能强行激活旧对象。

窄屏可把库列表和指法详情纵向排布，标题/底部取消与完成保持可达；低屏 Modal 的内容区内部滚动，整体不超过可视高度。网格不依赖 hover，触控目标至少 32px；六弦表可局部横向滚动，页面不横溢。快捷区换行不挤走“更多 ⌄”。不因屏幕断点重建编辑 owner 或清掉 local buffer。

## 11. 四阶段实施与验收标准

### 阶段 1：固定入口与共享选择契约

- 192 canonical identities 各至少一张审核通过且可弹奏图，热门列表各 2–3 个；别名不增计数，出具逐项覆盖记录。全部 16 性质和 24 大小调推荐可查询，自然/和声小调分组正确，理论调性拼写有用例。

### 阶段 3：图形编辑与单会话 Modal

- 6→1 网格、弦顶 0/×、单弦选品、null finger、两端点横按和表单替代可操作；无拖动必需步骤。

### 阶段 4：回归与真实证据

- 核心 Interface 测试：catalog 身份/aliases/quality/formula/最低音、覆盖计数、clone 隔离、图事务不变性和失败原子性；避免仅检查静态数组长度而漏掉无效指法。
- HTTP 资源测试：共享请求、相对 URL/basePath 解析、manifest/dataVersion 不符、未知 formatVersion、坏 JSON、HTTP/超时失败、首次失败重试、已有合法快照时保留、Modal 版本固定及迟到结果不误回填；验证项目静态 JSON 在开发/构建后实际可请求、请求缓存策略和资源一致性，不能只 mock 一个内存数组即记为 HTTP 完成。不要求第三方存储或跨域测试。
- HTTP 故障细项：manifest/catalog 共用总时限、响应流超限中止、超时后重试可恢复、旧请求不能清新请求状态；首载失败后在原 Modal 重试成功能进入首份快照，已持有快照的 Modal 不热切版本。相对 URL 只能解析到同源 chords 目录；缓存命中、404 HTML 回退与 dataVersion 不符有明确终态。加载失败不误判快捷引用永久丢失。
- preferences 测试：读写异常、200/6/体积上限、坏项/未知版/缺失引用、导入替换、同标签订阅与跨标签 revision 冲突；注入内存/失败 Adapter，不依赖真实浏览器 storage 来测纯规则。
- 调性 reader 测试：旧谱 `1=G` 无 mode 为 unconfirmed、无 key/扩展为 unset；`1=C + A minor/6` 与 `1=A + A minor/1` 均 confirmed 且推荐 A 小调；major 主音=1；minor 缺记法、缺 mode、malformed、未知 version、pc 不符、合法扩展配 null key 分别正确归类，均不泄漏本调推荐。拼写保留与等音 pc 校验分开验证，JSON 往返/旧谱显式升级保留其他 meta 和未知 namespace 内容。
- 曲谱信息命令测试：SetScoreInfo 的 undefined preserve/null delete/value set，执行时保留当前其他 meta；不一致候选原子拒绝；no-op 无历史，实际 apply 只一条历史且一次 undo/redo 恢复 key+mode+记法+拼写；旧命令改 key 的冲突守卫与不改 key 的标题编辑例外。设置 key/mode/记法整组 dirty 冲突不混合 rebase；设置预览不驱动 popup，取消不改 document/和弦草稿；一次应用不改音符、和弦名称/图或其他设置组。

## 12. 原型解释与审查边界

[prototype.html](../prototypes/chord-library/prototype.html)及[故障状态稿](../prototypes/chord-library/failure-states.html)是交互审查样本：包含部分指法示例、页面内配置和简化的错误/转场实现。它们没有交付 192 项、真实 HTTP、文件解析、持久化、完整 token gate 或全部公式审核；调性拼写采用有限示例表，搜索也仅演示显式根音/性质别名，不能代替正式算法与验收。56 项原型浏览器检查和两张新增评审截图已记录，产品侧的 4 阶段验收仍须另行完成。

原型已演示“基于此指法自定义”不先覆盖父草稿、选择与完成保留 display、横按候选冲突时保留原图。v2 原型/截图的审查要求是：曲谱来源标题与当前已提交曲谱一致；“设置曲谱调性”打开歌曲信息设置、应用后才刷新推荐；默认调内列表不混入 D/A/Bm/D7 等 C 大调非调内候选；搜索另标全库结果；我的常用与本调推荐分开；库默认跟随并明确临时浏览；缺图动作预先禁用且可查看详情。若样例初始显示 C 大调，原型应显式持有已提交的 `keySignature: 'C'` 与 `{ version: 1, tonic: 'C', mode: 'major' }` 曲谱信息，和设置 draft 分开；不能只固定标题或从“1=C”猜大调。上述为原型修订与审查约束，不代表产品能力或本轮已通过的验证。

正式实现仍需按第 3–8 节落实调性持久化与原子命令、完整原子选择、调式拼写、owner/token、独立 local buffer 和保留 display 规则，不能直接将原型脚本接入产品。用户审查通过交互稿和本方案后再进入四阶段实施；本轮未执行任何产品测试，也未声称目录数据或功能已交付。
