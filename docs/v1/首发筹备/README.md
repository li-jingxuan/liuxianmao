# 六线猫 v1.0 首发计划书

**评审建议**　让第一次见到六线猫的吉他老师在电脑上完成一件事：把四小节练习写成带和弦的六线谱，导出图片发给学生，第二天还能打开原谱改指法。首页用成品说明价值，Web 提供最短试用路径，Windows 和 macOS 桌面版承接本地写谱。对开发者，交付同一套编辑能力的两种入口：直接嵌入 React 组件，或用 JS Core 自己做界面。

这是供立项评审的计划。文中的角色、波次和投入都是建议，正式包名、授权和发布日期以评审决定为准。

| 工程、开源维护者 | [开源与三端交付](02-开源与三端交付.md) | 两个包的边界、公共 API、文档与安装包验收 |

## 二、为什么先做一份四小节谱

产品负责人约一位吉他老师编写可公开分发的原创练习，留下署名与授权记录，同时交付原生曲谱、A4 成品图和演示脚本。让学生第一眼就能看到要弹的内容，让开发者有数据可载入，也让测试有跨端比较的依据。现有示例与音频、字体、图标一并核对授权，仓库公开前核查拟公开文件及其历史中的凭证和内部配置。

验收用例建议选同一份谱做三件事：第一小节改一个品位并试听；第二小节加一个和弦并保存；整谱输出 A4，对照原稿检查和弦图、简谱和歌词。另选一份历史版本文件验证迁移，记录原文件版本、读取结果与重新保存的版本。[现行文件格式与输出行为](../design-baseline/score-files.md)

## 三、建议排期与分工

下面按相对周估算，假设有产品兼内容负责人、内核开发、应用开发各一人，以及可在两种桌面系统验收的测试协作者。实际日期由候选包、桌面签名条件及回归结果决定。

| 阶段 | 负责人 | 工作与依赖 | 完成标志 |
| --- | --- | --- | --- |
| 第 1 周：定范围 | 产品牵头，工程与运营参加 | 确认首发用户、支持平台与许可；挑选练习谱，整理编辑器全部 UI 操作与内核依赖；先落实签名账号、测试设备和 npm 权限 | 产品签下首发清单；明确每项授权或环境缺口的负责人 |
| 第 2–3 周：打通接入 | 内核开发负责双包，应用开发负责 Web 和 Electron | 先完成「打开、修改、保存」的最短路径，再补齐 UI 能力清单；首页梳理导航和搜索文案；内容负责人用同一谱备稿 | 两个候选包可在仓库外安装，三端交换原生文件；首页有可抓取的产品说明 |
| 第 4 周：小范围试用 | 测试牵头，邀请教师、独立开发者参与 | 用发布候选版完成上表各项；真机验证安装与输出，开发者仅凭 README 接入；运营根据卡点重录教程 | 保存测试记录、兼容矩阵、授权清单和已知问题；每项未通过能力有明确处理决定 |
| 首发日及随后两周 | 产品决定放行，维护者发包，运营分发 | 对齐包版本、GitHub 标签、安装包、下载链接和文档；先验证线上入口再发布教程。按渠道观察试用，按系统观察安装反馈 | 公开入口可走通，反馈有负责人；复盘结论进入下一轮修复或内容排期 |

**建议采用分批候选、一次宣布正式版。** Web 和两个 npm 包先供试用，桌面制品通过真机验收后再宣布三端齐备。若签名或安装验证拖期，产品负责人可以选择顺延统一首发，或批准 Web／npm 先行并单列桌面候选状态；下载区与宣传稿须同步标明实际可用版本。

## 四、首发评审要拍板的三件事

1. **产品范围和时间。** 确认网站首发首页与编辑器、桌面支持的系统版本及架构；选择三端齐发还是允许桌面延期。建议保留齐发目标，先安排候选版试用。
2. **开源授权与归属。** 明确公开源码范围、代码许可证、GitHub 与 npm 组织管理人，以及示例曲谱和素材的授权方式。建议先验证干净检出能构建，再邀请外部开发者试装。
3. **首发成效怎么算。** 创作者侧以完成首次有效编辑并导出曲谱或成品为主；开发者侧记录试用者能否仅凭公开文档跑通两条接入路径。建议第一周建立基线，再决定要扩哪个渠道。未经观测的播放量、搜索排名和 npm 下载量均不作为发布门槛。
