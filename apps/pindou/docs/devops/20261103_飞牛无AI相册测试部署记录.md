## 测试方式

首页临时改为“拼豆相册测试”，不调用 AI、不签发转换密钥、不查询或消耗转换额度。用户可以本机生成 128×128 PNG 或选择已有 PNG，再复用正式的保存→相册上传→入库→七天分享流程。预览和上传使用同一个 Blob，不压缩、不再次生成。

“检查 App 会话”仅读取当前会话，不保存图纸、不上传、不创建分享。诊断分为未收到桥、桥未就绪、调用超时、调用拒绝、返回字段无法识别和成功；“复制诊断”支持局域网 HTTP 和手动选区回退。诊断只含固定环境字段、白名单字段名及类型，不含 Cookie、凭据值、完整 UA、用户标识或原生异常内容。

网页默认入口仍可通过关闭 `NEXT_PUBLIC_FNOS_ALBUM_TEST_MODE` 恢复；普通 Web 镜像不受本次测试开关影响。

## 运行环境修正

旧包未声明官方要求的 `micro_app=true`；仅更换 Web 镜像不能确认宿主会注入桥。本次已通过同名 `pindou` 应用版本 `0.1.1` 的原位 FPK 升级写入微应用声明。此声明是运行环境前提，并不证明手机的 `getUserMessage` 一定存在或返回本适配器预期的凭据字段；仍需真实 App 验收。

FPK 从当前安装的公共包文件构建，保留项目名、实际挂载和 UI。最终 Web 镜像为 `pindou-fnos-web:album-noai-1696bbf-20261103`；API/proxy 使用保留源码重建镜像的独立别名 `pindou-fnos-api:noai-preserved-1696bbf-20261103` 和 `pindou-fnos-proxy:noai-preserved-1696bbf-20261103`，PostgreSQL 仍为 `postgres:17-alpine`。四个服务均配置 `pull_policy: never`，包检查中实际执行 Compose pull，四项均跳过远程拉取。安装后的 manifest 与应用中心成功结果只能证明包内容更新；App 是否刷新了缓存的微应用元数据，仍需手机完全退出并重开验证。

旧升级钩子会执行从过时主配置生成环境文件的脚本。测试维护包使用只校验现有配置的 `configure`，最终升级前同时保护已安装旧钩子。原脚本保存在私有备份及包内 `configure.original`。测试包依赖已存在的配置和数据，不用于全新安装；后续配置维护需要单独恢复正常配置流程。

首次 CLI 尝试没有替换包，检查拦住并恢复旧版本。随后使用应用中心更新向导，首个包因平台尝试从 Docker Hub 拉取本地镜像失败；平台退回旧包元数据并清理了部分本地镜像，导致飞牛服务暂时不可用。已从保留的精确部署上下文重建 API/proxy，从 BuildKit 缓存恢复旧 Web（镜像 ID 与原值一致），恢复旧服务及登录网关，再构建最终离线包。API/proxy 的重建镜像 ID 与原基线不同，验收额外比较容器内两个 API 源文件及 nginx 配置的 SHA-256，与保留部署源码一致。

最终通过应用中心 → 手动安装 → 从电脑上传完成实际更新。该向导在本包仅有提示步骤时，“下一步”直接提交 `/app-center/v1/update/task`；自动流程只有带 `--apply` 才保护旧钩子并提交更新。实际更新完成后逐项验收，不以进度对话框消失作为成功判据。
