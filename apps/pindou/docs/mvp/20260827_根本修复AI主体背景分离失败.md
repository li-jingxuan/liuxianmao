# AI 主体背景分离失败根本修复方案

> 状态：实施中（代码链路与首版模型已接入，效果集验收和生产灰度待完成）
>
> 日期：2026-08-27
>
> 范围：`apps/api` 的 Solid 背景前景准备链路，以及必要的部署、观测和响应契约调整
> 关联方案：[白色前景保留与视觉简化](./white-foreground-preservation-and-visual-simplification-plan.md)

## 1. 结论

根本修复不是继续加强 Prompt、反复调用 Seedream，或放宽键色阈值，而是把“生成视觉中间图”和“确定主体蒙版”拆成两个职责：

- Seedream 只负责把原图整理成适合拼豆量化的视觉中间图；
- 本地确定性的类别无关前景抠图（foreground matting）负责生成主体 Alpha 蒙版；
- Solid 请求统一运行本地前景模型；原生 Alpha 或键色最多作为未来的辅助诊断，不作为成功前提；
- 低置信只有在调用方显式设置 `fallback_mode=simplify` 时才改变语义；模型或运行时故障保持 503。

目标管线：

```text
上传图片
  → Seedream 视觉简化
  → 本地 ONNX 前景蒙版
  → 统一蒙版质量验证
  ├─ 可信：生成 RGBA 前景 → MARD 量化
  ├─ 低置信且允许降级：按 Simplify 量化并标记 degraded
  ├─ 低置信且不允许降级：422
  └─ 模型/运行时故障：503，不降级
```

其中，本地模型是 Solid 的权威路径，不依赖第三方模型是否遵守“输出透明背景”或“输出指定键色”的自然语言指令，也不需要再次调用付费生成接口。首版使用类别无关的 U-2-NetP 软显著前景蒙版；它不是物理精确的光学 Alpha Matte，因此必须保留质量验证、低置信拒绝和显式降级，后续可在不改变 `ForegroundPreparer` 外部 seam 的情况下替换为更高质量 Matting Adapter。

## 2. 问题与根因

### 2.1 当前失败条件

当前 Solid 模式要求 Seedream 满足以下任一条件：

1. 返回可信的原生 Alpha；
2. 返回覆盖画布边缘且可识别的内部键色。

Seedream 返回的图片通常完全不透明，因此第一条很少成立。第二条依赖生成模型遵守 Prompt，具有天然随机性。当键色边缘覆盖不足、键色偏离过大，或抠图后的主体面积超出保护阈值时，后端返回：

```text
AI_BACKGROUND_SEPARATION_FAILED
```

### 2.2 已验证的事实

使用 `docs/20260827-170938.jpeg`，在 `52×52 / balanced / solid` 条件下连续生成三次：

- 三次输出的 Alpha 都是完全不透明；
- 三次均选择内部键色 `#00FFFF`；
- 四边近键色覆盖率约为 `75.15% / 75.51% / 75.40%`；
- 三次恰好都高于当前 50% 门槛，因此成功。

这说明指定图片在当前时刻不稳定复现，但系统成功与否仍取决于随机生成结果，而不是确定性的图片处理能力。

仓库中的六张历史真实增强图均为完全不透明普通场景。把它们重放到当前前景准备逻辑后，六张都会触发同一稳定错误。历史图片由旧 Prompt 生成，不能用于计算当前 Prompt 的线上失败率，但足以证明“不遵循 Alpha/键色协议的生成结果”是现实存在且当前无法处理的一类输入。

### 2.3 根因

根因不是 50% 这个单一阈值，而是职责错位：

- Prompt 被用来承担结构化蒙版协议；
- 生成模型被当成前景分割模型；
- 本地实现只有验证和拒绝能力，没有独立生成蒙版的能力；
- 所以严格保护正确性后，只能把上游随机违约转化为用户可见错误。

降低阈值只会把“明确失败”变成“可能误删主体但表面成功”，不能作为修复。

## 3. 目标与非目标

### 3.1 目标

- Seedream 完全忽略 Alpha 和键色指令时，Solid 模式仍可确定性生成主体蒙版；
- 白色、浅色、低对比、毛发边缘和接触画布边缘的主体不因背景处理被大面积误删；
- 背景不进入 MARD 调色板和豆数统计；
- 相同增强图、模型版本和配置产生相同蒙版；
- 路由继续只消费一个准备完成的 RGBA 前景，不了解模型推理、键色或蒙版算法；
- 本地 Matting 失败可被精确观测，且不会伪装为普通用户输入错误；
- 运行时不下载模型，不把图片发送给新的第三方服务。

### 3.2 非目标

- 不让本地 Matting 模型直接生成拼豆网格或 MARD 色号；
- 不用无限重试掩盖分割失败；
- 不恢复“猜测边缘主色并无条件 flood-fill”的旧路径；
- 不通过保留最大连通域来假定图片永远只有一个主体；
- 不在缺少授权效果集和标注时拍脑袋确定最终置信度阈值；
- 不要求 `keep` 和 `simplify` 模式删除背景。

## 4. 架构决策

### 4.1 使用 `ForegroundPreparer` 形成外部 seam

随着依赖增多，继续让路由分别传入增强器、Matting Adapter、策略和诊断存储会扩大接口。改为由依赖工厂构造前景准备深模块，路由只调用一次准备操作：

```python
class ForegroundPreparer:
    def __init__(
        self,
        *,
        enhancer: ImageEnhancer,
        mask_adapter: ForegroundMaskAdapter,
        policy: ForegroundPolicy | None = None,
    ) -> None: ...

    def prepare(
        self,
        source: Image.Image,
        *,
        options: EnhancementOptions,
        fallback_mode: ForegroundFallbackMode = ForegroundFallbackMode.NONE,
    ) -> PreparedForeground: ...
```

路由只需要知道：

- 成功时得到可直接量化的 `PreparedForeground.image`；
- `processing` 描述实际采用的蒙版来源；
- 失败时得到稳定且可映射到 HTTP 的错误。

FastAPI 通过 `ForegroundPreparerDep` 注入已构造完成的对象。路由不知道实际模型、模型路径、阈值、诊断目录或回退顺序。以下实现细节全部留在模块内部：

- Solid 权威路径选择与显式 Simplify 降级；
- ONNX 输入预处理和输出还原；
- 软蒙版合成；
- 置信度与失败原因；
- 图片生命周期；
- 失败样本留存和结构化指标。

这样删除该模块后，复杂度会重新扩散到路由、增强器和量化器，说明该模块具有足够深度。

### 4.2 新增真实的内部 Adapter seam

本地 Matting 需要生产实现和测试替身，因此引入真实 seam。Adapter 只负责返回原始、与输入对齐的软蒙版；通用覆盖率、置信度和失败原因由 `ForegroundPreparer` 统一计算，避免不同模型各自定义不可比较的 `confidence`：

```python
@dataclass(frozen=True, slots=True)
class RawForegroundMask:
    mask: Image.Image  # mode=L，尺寸必须与输入一致
    model_name: str
    model_version: str


class ForegroundMaskAdapter(Protocol):
    def generate(self, image: Image.Image) -> RawForegroundMask: ...
```

Adapter：

- 生产：`OnnxForegroundMaskAdapter`；
- 测试：确定性 Mask Adapter，从内存返回冻结蒙版；
- 开发禁用：`UnavailableForegroundMaskAdapter`，只允许测试或明确关闭 Solid 能力的开发配置使用。

不要为 resize、normalize、阈值化和连通域清理分别建立公开接口；它们是 ONNX Adapter 的实现细节。生产环境启用 Solid 时如果模型不可用，应在启动阶段失败，不能注入 unavailable Adapter 后继续接收请求。

### 4.3 对增强后的图片做 Matting，而不是只处理原图

进入 MARD 量化的是 Seedream 增强结果，蒙版必须与增强结果的构图、尺寸和轮廓逐像素对齐。因此权威分割输入是 `enhanced`，不是上传原图。

原图蒙版可用于离线效果评估或未来的一致性约束，但不能直接覆盖到可能已经改变构图的增强图上。

## 5. Solid 模式处理流程

### 5.1 完整决策顺序

```text
1. 调用 Seedream 生成普通不透明增强图；Prompt 不再要求 Alpha 或内部键色
2. 对增强图执行本地 ONNX 前景推理
3. 统一验证软蒙版
   ├─ 可信：采用 local_matte
   ├─ 低置信 + fallback_mode=simplify：采用 fallback_simplify
   ├─ 低置信 + fallback_mode=none：返回 422
   └─ 模型排队、加载或运行故障：返回 503
4. local_matte 用软蒙版替换增强图 Alpha，再交给 MARD 量化
5. fallback_simplify 保留整张增强图量化，响应明确返回 degraded=true
```

`simplify` 降级只处理内容低置信，不能捕获 503 后继续返回成功，否则会把部署或容量故障伪装成正常业务结果。同一次请求不重复扣费；降级复用已经得到的增强图，不再次调用 Seedream。

### 5.2 不把自动重试放入正确性主链

Seedream 重试只能降低随机违约概率，不能保证正确性，而且增加费用与响应时间。因此：

- 不把“重试一次”作为根本修复的完成条件；
- 网络超时、限流等上游瞬时错误仍按现有错误映射处理；
- 只有后续真实指标证明某类失败适合低成本重试时，才把有限重试作为独立性能/可用性策略；
- 无论是否重试，本地 Matting 都必须可以处理普通不透明增强图。

### 5.3 统一蒙版质量验证

所有生产 Adapter 输出都进入统一验证器，避免更换模型后产生互相矛盾的成功定义。

至少检查：

- 前景总覆盖率；
- 完全透明、完全不透明和软边缘像素占比；
- 蒙版不确定区域占比；
- 最大连通前景和其他连通前景占比，但不无条件删除小主体；
- 前景是否从边缘异常贯穿整张图；
- 输入与蒙版尺寸是否一致；
- 主体接边时不得仅因边缘不透明而失败；
- 合成后背景残留是否超过效果集门槛。

阈值通过固定效果集标定，并集中在不可变的 `ForegroundPolicy` 中。配置只允许选择经过测试的策略版本，不允许线上任意修改单项阈值后形成不可复现结果。

### 5.4 软 Alpha

模型必须直接输出 Alpha Matte，或使用“类别无关粗分割 + Matting 边缘细化”的组合。普通语义分割概率只是类别置信度，不等价于光学 Alpha，不能未经验证就直接用于合成。最终 Matte 应保留为软 Alpha，而不是直接二值化：

- 高置信前景映射到接近 255；
- 高置信背景映射到接近 0；
- 毛发和抗锯齿边缘保留连续过渡；
- 仅在极低概率噪点和明显孔洞上做小尺度确定性修正；
- 不做会吞掉白色主体、细肢体、耳朵、尾巴或 Logo 的大范围腐蚀/膨胀；
- 最终是否放豆仍由网格采样的 Alpha 覆盖率决定。

## 6. ONNX 模型选型与交付

### 6.1 任务定义与选型原则

Solid 的领域语义定义为：保留画面中的所有主要显著主体及其可见结构，移除环境、地面、投影和无关背景物体；主体内部天然孔洞保持透明，附着在主体上的身份性配件保留。阴影、倒影、半透明物体和次要主体必须在效果集标注规则中明确，不能交给每个模型自行解释。

首版固定使用 U-2-NetP：类别无关、Apache-2.0、约 4.4 MiB、320×320 输入，适合作为 CPU/NAS 上的轻量基线。其输出是软显著前景概率而非物理精确 Alpha；选择它是为了先消除 Seedream 格式协议依赖，不代表已经通过最终质量门槛。替换候选必须是类别无关显著主体 Matting，或能与 Matting 精修组合的类别无关前景分割；仅人像分割、固定类别语义分割和目标检测模型不满足要求。模型必须同时满足：

- 支持人物、动物、商品、动漫和未知显著主体，而非只支持人像或固定类别；
- 可在 CPU 上离线推理；
- 可导出或原生提供稳定 ONNX 图；
- 商业使用和再分发许可清晰；
- 输入输出预处理公开且可固定版本；
- 对白色主体、浅色背景、毛发、透明物体、内部孔洞和主体接边有可接受表现；
- 模型体积、峰值内存和延迟适合现有 NAS/Docker 部署。

必须记录：模型来源、许可证、版本、SHA-256、输入尺寸、归一化参数、输出语义和评测报告。

### 6.2 固定模型版本

生产运行时不得联网下载模型。推荐目录：

```text
apps/api/models/foreground/
  u2netp.onnx
  model.json
  LICENSE
```

`model.json` 至少包含：

```json
{
  "name": "u2netp",
  "version": "rembg-v0.0.0-u2netp",
  "sha256": "309c8469258dda742793dce0ebea8e6dd393174f89934733ecc8b14c76f4ddd8",
  "input_size": [320, 320],
  "license": "Apache-2.0"
}
```

如果模型不适合直接进入 Git，则使用 Git LFS 或构建期受控制品输入，但最终镜像必须包含固定模型和校验信息。容器启动时校验 SHA-256，校验失败则健康检查不通过，不能静默退回只靠 Prompt 的模式。

### 6.3 运行时

新增并固定 CPU ONNX Runtime 与 NumPy 直接依赖。实现必须显式选择 `CPUExecutionProvider`，不能依赖机器上“恰好可用”的 Provider 顺序。当前 ONNX Runtime 提供 Python 3.11–3.14、Linux x86-64 和 ARM64 预编译 wheel，但仍需在实际 NAS 架构、基础镜像 glibc 和固定 Python 版本上构建验证。运行时明确：

- Session 进程级缓存，不在每个请求中加载模型；
- FastAPI lifespan 启动时加载、校验并执行一次小图 warm-up；
- 固定 `onnxruntime`、`numpy`、模型和预处理代码版本；
- 显式配置 `ORT_SEQUENTIAL`、`intra_op_num_threads` 和线程 spinning；ONNX Runtime 默认可能使用接近物理核心数的线程，NAS 上不得沿用未标定默认值；
- 推理线程数按部署 CPU 标定，避免 ONNX Runtime 与 FastAPI/Uvicorn 线程池相互过量并发；
- 使用独立有界信号量限制 Matting 并发；
- 单个 Uvicorn worker 对应一个 Session 和一份模型内存；增加 worker 前必须按 `worker 数 × 单 Session RSS` 验证内存，首版生产保持单 worker；
- 推理超时或运行时异常映射为内部服务错误，不伪装为“图片无法识别”；
- 输入图片先等比缩放并补边到模型尺寸，输出蒙版再精确反变换到增强图尺寸。

建议配置：

```dotenv
FOREGROUND_MASK_ADAPTER=onnx-matting
FOREGROUND_MODEL_PATH=/app/apps/api/models/foreground/model.onnx
FOREGROUND_MODEL_METADATA_PATH=/app/apps/api/models/foreground/model.json
FOREGROUND_MASK_MAX_CONCURRENCY=1
FOREGROUND_MASK_QUEUE_TIMEOUT_SECONDS=3
FOREGROUND_ONNX_INTRA_OP_THREADS=2
FOREGROUND_ONNX_ALLOW_SPINNING=false
FOREGROUND_POLICY_VERSION=foreground-v1
```

这些配置选择经过测试的实现、资源预算和策略版本，不直接暴露几十个可漂移阈值。镜像构建必须显式 `COPY apps/api/models/foreground`，模型放在独立缓存层；运行时不从公网下载。模型制品只能来自可信来源，构建阶段校验 SHA-256、许可证和模型元数据，依赖进入锁定与漏洞扫描流程。

### 6.4 健康与就绪

- 模型缺失、SHA-256 不符、Session 创建失败或 warm-up 失败：应用启动失败；
- 启动后的 `/readyz` 同时检查数据库和 Adapter 已加载状态；不以“当前信号量有空位”作为就绪条件，避免正常短时满载导致实例被反复摘除；
- Docker Compose 健康检查从 `/healthz` 改为 `/readyz`；
- 单次推理异常不永久把实例标记为 unavailable，但连续运行时错误应进入告警并触发实例重启策略。

`/healthz` 只表示进程存活，不能继续作为接收流量的唯一条件。

### 6.5 当前实测结果与限制

已在 Linux ARM64、Python 3.12、ONNX Runtime 1.29.0、`CPUExecutionProvider` 环境对
`docs/20260827-170938.jpeg` 执行完整 `ForegroundPreparer` 链路：输出
`local_matte`，置信度约 `0.9642`，尺寸保持 `1179×1168`。人工合成到高对比背景后，
金毛主体和主要毛发轮廓被完整保留；左耳附近仍可见少量与主体相连的暗背景残留。

因此该样本证明“Seedream 不返回 Alpha/键色时链路仍可继续”，但不能单凭内部覆盖率
置信度宣称最终视觉质量达标。上线前仍需完成多类别效果集、最终拼豆网格背景残留和
主体误删的人工验收；若 U-2-NetP 未达门槛，应替换 Adapter，而不是放宽验证阈值。

## 7. 错误、额度与降级语义

### 7.1 错误分类

区分图片确实无法可靠分离与系统能力不可用：

| 场景 | HTTP | 稳定错误码 | 语义 |
| --- | ---: | --- | --- |
| 本地蒙版低置信且未允许降级 | 422 | `AI_BACKGROUND_SEPARATION_FAILED` | 当前图片无法安全生成主体蒙版 |
| 本地蒙版低置信且允许降级 | 200 | 无 | 返回 `fallback_simplify` 和 `degraded=true` |
| ONNX 模型缺失、校验或 warm-up 失败 | 不接流量 | 启动失败 | 部署或制品故障 |
| ONNX 推理排队超时 | 503 | `FOREGROUND_MASK_BUSY` | 本地推理暂时不可用 |
| ONNX 单次运行时异常 | 503 | `FOREGROUND_MASK_UNAVAILABLE` | 当前实例推理异常 |
| ONNX 输出尺寸、NaN 或数值范围非法 | 500 | `FOREGROUND_MASK_INVALID_OUTPUT` | 实现或模型契约错误 |

生产环境配置为 Solid 可用时，模型缺失不得静默跳过，否则系统会回到本方案要消除的不稳定状态。只有模型成功加载并通过 warm-up 后实例才可 ready。

### 7.2 额度

同一个转换请求内部无论经过几条蒙版路径，只扣一次额度。本地 Matting 不是新的用户操作，不重复扣费。

本方案实施时至少做到：

- 503 类内部能力故障不应消耗用户额度；
- 422 类内容低置信是否扣次需要形成明确产品规则；
- 不因一次 HTTP 请求内部执行了本地 Matting 而增加扣次；
- 记录 503 与 422 对额度的实际影响，为独立额度方案提供基线。

预占/确认/释放涉及表结构、崩溃恢复和并发语义，不作为本背景修复的实施阻塞项，应另立方案并补 Alembic 迁移、repository、幂等和并发测试。在独立方案落地前，不在本文件中承诺自动退款；但内部 503 持续扣次必须作为已知产品风险记录和监控。

## 8. 响应契约

公开网格 schema 保持不变，只扩展实际处理方式：

```python
background_processing: Literal[
    "none",
    "local_matte",
    "fallback_simplify",
]
```

响应可以增加非敏感诊断：

```json
{
  "background_mode": "solid",
  "applied_background_mode": "simplify",
  "degraded": true,
  "degrade_reason": "foreground_low_confidence",
  "background_processing": "fallback_simplify",
  "foreground_model_version": "rembg-v0.0.0-u2netp"
}
```

正常 Solid 示例：

```json
{
  "background_mode": "solid",
  "applied_background_mode": "solid",
  "degraded": false,
  "background_processing": "local_matte",
  "foreground_model_version": "rembg-v0.0.0-u2netp"
}
```

不要向客户端返回：

- 模型绝对路径；
- 原始概率图；
- 内部蒙版阈值；
- 完整 Prompt；
- 失败图片位置。

Web 端提交 `fallback_mode=none|simplify`；收到 `degraded=true` 时必须明确提示结果包含背景，不能把降级伪装成 Solid 成功。

### 9.1 结构化指标

每次 Solid 请求记录：

- `request_id`；
- `enhancer`、模型和 Prompt 版本；
- `foreground_policy_version`；
- `background_processing`；

- 总耗时与峰值并发等待时间。

### 9.2 失败样本必须在关闭前留存

当前备份发生在前景准备成功之后，无法保留最有价值的失败增强图。改为由前景准备模块通过受控诊断存储记录：

```text

```

要求：

- 仅保存增强图，是否同时保存用户原图由显式隐私配置决定；

## 10. 测试与效果集

### 10.1 接口测试

测试只穿过 `ForegroundPreparer.prepare()` 外部 seam，使用假增强 Adapter 和固定蒙版 Adapter，不围绕内部 ONNX tensor 或 flood-fill 细节堆叠浅测试。

必须覆盖：

- Solid 即使收到有效 Alpha 或普通不透明图，也统一调用本地 Adapter；
- 普通不透明场景通过本地 Matte 成功；
- Matting 返回软边缘时 Alpha 连续保留；
- 白色主体与白底接触时主体不被删除；
- 金毛、毛发、耳朵和细尾巴不被大范围腐蚀；
- 主体接触任意一条或多条画布边缘；
- 多主体和多个非连通主体均被保留；
- 蒙版近全空、近全满、含 NaN 或尺寸错误时稳定失败；
- 本地 Matte Adapter 运行时不可用时返回 503 类错误；
- 低置信且 `fallback_mode=none` 时返回 422；
- 低置信且 `fallback_mode=simplify` 时返回明确降级结果；
- 503 即使允许 fallback 也不得降级；
- `keep/simplify` 不调用 Matting Adapter；
- 成功后白色前景获得 MARD 色号并计入豆数；
- 所有成功、异常和超时路径都正确关闭 Pillow 对象。

### 10.2 ONNX Adapter 契约测试

- 输入归一化与模型元数据一致；
- 非方图 resize/pad/unpad 可逆；
- 输出蒙版与原图尺寸完全一致；
- 固定输入在相同镜像、Runtime、Provider 和硬件下重复输出一致；跨 CPU 架构按数值容差和质量指标比较，不要求二进制哈希一致；
- 模型 SHA-256 不一致时启动失败；
- 全黑、全白、极小图和最大允许图不会崩溃；
- 多线程或并发请求不共享可变 tensor 状态。

### 10.3 固定效果集

效果集至少包含：

- `docs/20260827-170938.jpeg`；
- 仓库中已有的真实增强输出；
- 白衣、白色动物、浅色商品与白底；
- 黑色主体与暗背景；
- 人物、宠物、商品、动漫、多主体、透明物体；
- 主体贴边、主体很小、主体占满画面；
- 毛发、细肢体、复杂轮廓、低对比边缘；
- Seedream 普通不透明场景、低对比背景和渐变场景输出。

AI 生成阶段每个组合至少运行三次；分割和量化评估使用冻结后的增强图，确保对比确定。

### 10.4 上线门槛

以下是首轮验收目标，最终数值需在目标部署机器和已授权效果集上确认：

- Solid 严重背景分离失败率低于 1%；
- 标注效果集主体区域 IoU 不低于 0.92；
- 增加 Boundary F-score、Alpha SAD/MAD 和 trimap 未知区域误差门槛，具体值由候选模型基线标定后冻结；
- 白色/浅色主体关键区域召回率不低于 0.98；
- 记录最终网格的主体误删格、背景残留格和豆数偏差，严重误删必须为 0；
- 不允许出现主体核心被大面积清空的严重错误；
- 固定输入在相同镜像、Provider 和硬件上重复运行一致；跨架构满足冻结数值容差；
- CPU warm 状态 Matting P95 不高于 1 秒；
- Matting 峰值 RSS、镜像增量和冷启动时间满足 NAS 部署预算；
- 100% 请求不需要运行时联网下载模型。

如果模型无法满足人物、动物和商品的统一门槛，应选择更合适模型或明确拆分策略，不能通过降低蒙版质量验证掩盖问题。

## 13. 明确拒绝的替代方案

### 13.1 只加强 Prompt

Prompt 可以提高遵循率，但不能把概率性生成变成结构化蒙版协议，不能作为正确性保证。

### 13.2 失败后只重试 Seedream

重试降低概率但不消除根因，同时增加付费调用、延迟和输出波动。可作为独立可用性优化，不能替代本地 Matting。

### 13.3 降低 50% 键色边缘覆盖门槛

当模型输出普通场景时，放宽阈值会把背景物体或主体边缘误判为键色，产生不可见的数据错误。

### 13.4 恢复猜边缘颜色的 flood-fill

该路径已被证明可能沿轮廓缺口进入白色主体，导致白色区域不计豆。它可以处理少量理想纯色背景，但不具备通用语义。

### 13.5 只对上传原图做 Matting

Seedream 可能改变构图、比例和轮廓，原图蒙版无法保证与增强图对齐。权威蒙版必须基于实际进入量化的增强图。

### 13.6 调用新的第三方抠图接口

这会增加图片外发、网络依赖、费用、超时和隐私风险。除非本地候选模型全部无法满足效果门槛，否则不作为首选。

## 15. 技术依据

- [ONNX Runtime Python API](https://onnxruntime.ai/docs/api/python/api_summary.html)：明确 `InferenceSession` 和 Execution Provider 的配置方式；本方案显式指定 `CPUExecutionProvider`，不依赖环境中的隐式 Provider 顺序。
- [ONNX Runtime 线程管理](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)：说明了 intra-op 线程、执行模式和 spinning 的行为；本方案因此要求显式限制线程数并在目标 NAS 上压测。
- [onnxruntime PyPI](https://pypi.org/project/onnxruntime/)：用于核对发布版本、Python 版本和平台 wheel 兼容性；实施时应以锁定文件和目标镜像实测结果为准，不仅依赖开发机安装成功。
