# NAS 两套部署的统一目录与配置

本机管理根目录为 `/vol2/1000/apps/liuxianmao/apps/pindou/`。普通 Web 与飞牛版分别使用 PostgreSQL 容器和数据库；只统一配置入口，不合并数据库，不重置旧访问密钥。

```text
apps/pindou/deploy/
├── .env                        # 唯一手工维护的主配置，0600
├── configure.py                # 校验并生成运行配置，不执行 shell
├── run.py                      # 统一配置的 Compose/打包入口
├── compose.yaml                # 普通 Web 项目 pindou
├── .runtime/                   # 自动生成，不手工维护，不提交 Git
│   ├── web.env                 # 普通 Compose 插值参数
│   └── web-api.env             # 普通 API 专用变量
├── data/                       # 普通版 PostgreSQL、图片、日志、交付图
├── backups/migration-20261102/  # 本次迁移备份，含私密配置、数据库与文件
└── fnos/
    ├── data/                   # 飞牛版 PostgreSQL、图片、日志、交付图
    └── compose.installed.yaml  # 本机安装配置参考副本（实际由应用中心管理）
```

飞牛平台仍管理 `/var/apps/pindou/target`、`cmd` 与 Socket。其 `etc/api.env`、`etc/postgres.env` 是由主配置生成的运行文件；不用再手工维护。数据通过绝对路径 bind mount 挂载到 `deploy/fnos/data/`，不依赖移动系统符号链接。泛用 FPK 未设置 `FNOS_DATA_DIR` 时仍使用平台 `TRIM_PKGVAR`。

## 环境变量规则

主配置示例见 [`deploy/unified.env.example`](../../unified.env.example)。普通变量作为 Web 值及飞牛默认值；`FNOS_` 前缀覆盖飞牛对应变量，例如 `FNOS_API_KEY_HASH_PEPPER`。配置生成器不会把另一套管理密钥和数据库密码带入 API 容器。

本次迁移以运行容器的有效配置为准，保存两套原管理密钥、数据库密码、Pepper、模型与其他参数。两套相同的参数只写一次；已有差异通过 `FNOS_` 项保留。若需要统一某个模型或并发参数，可在主文件中调整公共值并移除对应 `FNOS_` 覆盖。两套数据库凭据和 Pepper 保持原值。

值使用 JSON 双引号，字面 `$` 编码为 `$$`；禁止 `source deploy/.env`。修改前先备份。以下命令都从 `apps/pindou/` 执行：

```sh
sudo vi deploy/.env
sudo python3 deploy/configure.py --fnos-etc /var/apps/pindou/etc
sudo python3 deploy/run.py web config --quiet
sudo python3 deploy/run.py web up -d --no-build --wait
```

AI 读取超时统一使用 `ARK_DOUBAO_READ_TIMEOUT_SECONDS="300"`，不要用 `FNOS_ARK_DOUBAO_READ_TIMEOUT_SECONDS` 覆盖成旧值。飞牛代理读取、发送超时均为 420 秒，为上传和本地处理留出时间；修改代理配置后也需更新对应镜像。

配置渲染只写生成文件，不自动停止容器。飞牛侧需重建受影响服务才能重读 env，`docker restart` 不会刷新环境变量。更新前通过应用中心正式停止拼豆，在停止状态下创建更新后的容器，再由应用中心启动；生命周期脚本不重复启动 Compose：

```sh
sudo appcenter-cli stop pindou
sudo env TRIM_APPDEST=/var/apps/pindou/target \
  TRIM_PKGETC=/var/apps/pindou/etc TRIM_PKGVAR=/var/apps/pindou/var \
  docker compose -p pindou-fnos \
  -f /var/apps/pindou/target/docker/docker-compose.yaml \
  create --force-recreate
sudo appcenter-cli start pindou
sudo appcenter-cli status pindou
```

仅更新 Web 时可将 `create --force-recreate` 改为 `create web`，Compose 会保留配置未变的依赖容器。NAS 当前版本的 `compose create` 不支持 `--no-deps`；该选项不能从 `compose up` 命令直接照搬。

应用中心显示 `running` 后，继续检查登录后的 `/app/pindou/`、静态资源和 API，并在后续监测周期再次确认状态。不能只用容器 `healthy` 或 `cmd/main status` 判定应用已恢复：平台运行期间直接重建容器，短暂不健康会触发 `APP_CRASH`，容器恢复后平台可能仍停在 `start` 状态且网关返回 404。此时应通过应用中心停止、启动应用以重新注册入口，不重启整个 NAS 或网关服务。

本机安装的飞牛 `cmd/configure` 也读取主配置生成 fnOS env，因此不能在飞牛配置向导另填方舟密钥，避免双重配置来源。主配置缺失时应报错，不自动生成新密钥。

## 重新构建

普通版使用 `sudo python3 deploy/run.py web build`，然后 `sudo python3 deploy/run.py web up -d --no-build --wait`。飞牛镜像使用 `sudo python3 deploy/run.py fnos images`，打包用 `sudo python3 deploy/run.py fnos package`。两种 Web 前缀不同，必须使用各自标签与构建参数。`FNOS_DATA_DIR` 及主配置路径写入本机专用安装包的元数据；该包不能原样分发到目录不同的 NAS。

需要创建受限 BuildKit 构建器时，见[飞牛包构建说明](../README.md#构建发布与打包)。构建器与构建命令应使用同一系统用户（上述命令为 root），并将主配置的 `DOCKER_BUILDER` 设为该用户下实际存在的构建器。本次镜像使用固定已提交源码版本，未部署工作区中正在开发的 UI 功能。重新构建 PostgreSQL 指重建容器，继续使用 PostgreSQL 17 镜像，保留原数据库数据。

`buildx_buildkit_pindou-managed-builder0` 是镜像构建器的临时容器，运行拼豆不依赖它。构建完成后可停止构建器，再移除其已停止的容器，保留命名卷中的构建缓存和 buildx 元数据；不要删除缓存卷或执行全局 prune。BuildKit 收到停止信号时可能退出为 1，在 Docker 界面中显示异常不等于拼豆运行服务异常。

## 验收与回滚

迁移时停止业务写入，分别备份两套数据库、配置和数据文件；保留 UID/GID、文件权限与扩展属性。物理复制通过 rsync 校验，重建前后对比全部数据库表的行数及内容摘要。验收还包括旧密钥查询、页面、图片、Socket 与普通 API readiness；不自动调用付费转换。

飞牛共享目录可能使复制或归档后的文件显示为 `000` 权限。迁移时须核对源/目标目录的模式及 ACL；API 镜像也显式设置应用代码的读取和遍历权限，避免非 root 用户无法读取 Alembic 配置。停止后的数据库才能做物理复制，校验失败时不切换数据源。

清理 `projects/` 前，扫描所有容器挂载，确保无旧路径引用；只删除已备份且确认属于拼豆的数据和空父目录。迁移前备份位于 `deploy/backups/migration-20261102/`，不能对外分享或提交 Git。若需回滚，先停止两套应用，从该目录恢复原配置和对应数据库/文件备份，再重建原镜像容器；不能向运行中的数据库覆盖物理备份。
